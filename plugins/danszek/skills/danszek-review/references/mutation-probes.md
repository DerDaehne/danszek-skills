# Mutation probes

Read this before running mutation probes, in a review or on your own tests. The rule in the main skill applies: revert each fix alone → its test must fail; break the invariant each new test *names* → that test must fail; a surviving mutant is a finding unless you can show it is unobservable.

## Where and how
- In a throwaway clone or a separate worktree, never the stash (it is shared by every worktree of a repository) and never destructive resets in shared trees.
- **The clone holds what you think it holds.** A clone has only committed work: commit before cloning, or the fix under test is missing. A clone of a worktree checks out the main repository's current branch, not the worktree's: check `git branch --show-current`, or a probe on the wrong branch passes silently. Re-clone instead of "resetting" a used clone (a soft reset left earlier mutants staged; a reset before the run restored the old code). A build that sees only tracked files leaves an untracked new test file out without a word: add it first.
- **The mutant is in place:** right before the run, grep for it in the tree the run builds. A script that edits code by matching text says which file and line it matched and fails loudly on no match; a missing argument once applied no mutation, and a regex once hit an identical line in another function. Read each mutant's diff before counting its result.
- **Keep it cheap:** run the test runner directly against already-built artefacts with the environment taken from the check's build definition, and keep a clone with only the affected test files; each mutant then takes about a minute instead of a full build. Batch mutants that hit different test files into one build. Take import paths from the check's definition, not from a helper written for another branch: a stale module path made the baseline look red.
- Run probes while nothing else loads the machine, and repeat edge results: a mutant at the boundary passed once and failed later under different load.

## The mutant must be real
- Confirm a non-empty diff (a substitution that matched nothing once "confirmed" an unchallenged test) and valid code (one mutant "failed" only because the engine lacked a function it called; read the failure message).
- Confirm it changes behaviour: deleting a property set to its library default changes nothing, so look up the default and mutate to the opposite; a mutated rule that another check also enforces is a no-op; a mutant in a caller that only feeds a path the callee returns early on changes nothing. Replacing a fixed wait by firing its timer can silently drop a deferred call the wait let run; probe every such swap.
- **Narrow it to the state under discussion.** To test a deliberate *absence* of a guard, block exactly that state: a mutation that blocks every call also kills the follow-up calls and looks "caught".
- A mutant the author declares "equivalent" needs a proof or a probe; one such claim hid a real effect on a later question.

## Where to mutate
- **Where the author did not:** the author's own probes cover the paths they thought of. Mutate the guards and the disabled paths first ("does nothing when …", "no call when off"), every guard the diff touches, old ones included (a change that makes a guard's precondition rare often comes with rewritten tests that pass trivially), and every behaviour the author claims. A developer's own note "this edge case is untested" is settled fastest by a mutant that removes exactly that behaviour.
- **From the criteria:** derive at least one mutant from each acceptance criterion's exact wording ("keeps the newest entry"), not only from the changed lines; diff-based mutants missed it.
- **Each half on its own:** one of two symmetric handlers (X and Y; suites usually cover one axis), each handler of code that listens to several signals, each place a flag is cleared (not only where it is read), each half of a combined reset, each step of an if/else-if chain (taken out of the chain, not only its constants: tests written from edge cases miss "the first step wins even when the last would choose otherwise"), each half of a two-part fix. Mutating the whole mechanism at once hides the untested half.
- **Control flow and callers:** mutate `continue` to `return`, not only conditions; mutate the callers of a changed signature too, since a stand-in that drops new arguments lets a broken caller pass. A sticky flag is also probed with the object it refers to destroyed: the reference clears itself, the flag does not.
- **Thresholds and inputs:** move a threshold by one at the exact boundary (`>` to `>=`); moving it far proves little. A mutant can be equivalent only for the test's inputs: integer coordinates could not separate `>` from `>= +1`, a diagonal move could. A test that moves "by the threshold" moves with the mutated threshold; use literal values. Change one input at a time: a width that also changed the column count let a fresh recompute hide the faulty state. For "the user's value wins", mutate to a stronger priority, not only to absence. A survivor among small off-by-one mutants on shared code means the tests check ranges, not exact values: assert the exact result per branch.
- **Input kinds:** when a mutant stays green, try every input kind (touch as well as pointer, key as well as click) before calling the guard covered.
- **Static checks** (a grep or source-level guard): put the old pattern back in a different file than the author's own probe used.
- **Trust boundaries:** put a canary into input that crosses a process boundary (`$(touch marker)` in a name or argument) and check that the marker file does not appear.
- **Ports:** random-input equivalence against the reference proves a port exact, but only mutants show whether the tests pin each rule; an exact port had tests that let five of seven rules change unnoticed.
- **Code no test loads** (a native plugin, a packaged extension): mutate it in a package build and probe it live.

## Reading survivors
- A survivor is not automatically a missing test: the test may reach the path but cannot observe the change (undo cannot run twice once its toast closed) — come from another direction; in a race, read how wide the window really is, since some orderings can only be shown correct from the source. Before trusting a survivor, rewrite the assertion that should catch it as a strict check that fails visibly: a framework's fuzzy compare passed where a strict identity check saw the wrapped value.
- **A rewritten test** is checked by running the same mutant against the old and the new test file: "all mutants caught" alone hides a weakening.
- **To prove a refactor left a test empty,** run the same mutant on the branch and on main and list the tests red only on main; it finds what a name audit misses.

## Rounds and rebases
- **Re-reviews:** re-run the first round's mutation script unchanged on the fix round, then add one mutant aimed at the new logic. Keep probes as plain test functions that can be appended to the current test file; re-running them then takes minutes. A fixer runs the reviewer's probe exactly as written against the fix: the suite was green once while the probe itself was not.
- **Rebuild before end-to-end probes** that run a build artefact, or the probe tests old code and a "surviving mutant" is false. A build tool that caches checks by input replays an old verdict; force the rebuild with full logs. **Re-run the probes on the rebased commit**, the state that actually merges.
